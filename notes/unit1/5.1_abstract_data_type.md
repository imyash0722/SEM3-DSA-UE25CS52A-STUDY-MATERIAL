# Unit 1: Abstract Data Types (ADT)

## 6.1 Concept of Type

### Mathematical Foundation:
- **Set** + **Operations** = Type
- **Integers (ℤ):** Closed under +, ×
- **Operations** have many implementations (column add, Vedic math, tally marks)
- **Result is SAME** regardless of implementation

### Programming Type:
| Aspect | Description |
|--------|-------------|
| **Values** | What values are legal (e.g., `int`: -2³¹ to 2³¹-1) |
| **Operations** | What you can do (+, -, *, /, %) |
| **NOT specified** | HOW operations work (implementation) |
| **Uniformity** | All values of type treated same way |

### Type Systems:
| Language | Type Binding | When Determined |
|----------|--------------|-----------------|
| **C** | Static | Compile time (must declare) |
| **Python** | Dynamic | Runtime (value determines type) |

## 6.2 The Problem: Real-World Types

### Can a language support ALL real-world types?
**NO!** Too many: car, fan, phone, browser, dream...

### Solution: **User-Defined Types** → **Abstract Data Types (ADT)**

---

## 6.3 What is an ADT?

### Definition:
An ADT is a **user-defined type** that:
1. **Specifies WHAT operations do** (interface)
2. **Does NOT specify HOW** (implementation)
3. **Interface = Sacred** (cannot change once published)
4. **Implementation = Flexible** (can change without affecting users)

### Car Analogy:
| Aspect | Car Example | ADT Equivalent |
|--------|-------------|----------------|
| **Interface** | Brake pedal, steering wheel | Function signatures |
| **Implementation** | Hydraulic brakes, power steering | Function bodies |
| **Change** | Mechanical → hydraulic brakes | Rewrite function body |
| **Can't change** | Brake pedal makes car accelerate | Function signature |

### Key Principles:
| Principle | Description |
|-----------|-------------|
| **Interface is sacred** | Once published, never change |
| **Implementation hidden** | User depends on interface, not internals |
| **Inversion of dependency** | Both user & implementor depend on interface |
| **Change implementation freely** | User code unaffected |

---

## 6.4 Data Structures as ADTs

### Data Structure = ADT + Efficiency Constraints
```
Data Structure = 
  Interface (ADT) + 
  Time/Space Constraints
```

### Example: List ADT
| Interface | Implementations |
|-----------|-----------------|
| **Operations:** Create, Destroy, Insert, Delete, Access | **Linked List** (dynamic, O(1) insert/delete) |
| **Constraints:** Sequential access, no random access | **Array** (fixed size, O(1) random access) |

### Trade-offs (No "Right" Answer):
| Arrangement | Space | Access | Concurrency |
|-------------|-------|--------|-------------|
| **Vertical (stacked)** | Saves space | One access at a time | Sequential |
| **Horizontal (side-by-side)** | More space | Multiple simultaneous | Parallel |

## 6.5 List ADT Specification

### Properties:
- Zero or more components
- Each element has **ordinal position** (1st, 2nd, 3rd...)
- **Sequential access** (no random/direct access)
- Cannot jump to position N directly

### Interface (Operations):
| Operation | Purpose |
|-----------|---------|
| `create()` | Initialize empty list |
| `destroy()` | Release all resources |
| `insert(pos, val)` | Insert at position |
| `delete(pos)` | Remove at position |
| `get(pos)` | Access element |
| `size()` | Number of elements |
| `is_empty()` | Check if empty |

### Two Implementations:
| Aspect | Linked List | Array |
|--------|-------------|-------|
| **Memory** | Dynamic (heap) | Fixed (compile-time) |
| **Insert/Delete** | O(1) at known position | O(n) shift |
| **Access** | O(n) sequential | O(1) random |
| **Memory overhead** | Pointer per node | None |

---

## 6.6 Inversion of Dependency

### Traditional (Bad):
```
User Code → depends on → Implementation
```
Change implementation → breaks user code

### ADT Pattern (Good):
```
User Code → depends on → Interface ← depends on → Implementation
```
- Interface is **stable contract**
- Implementation can be swapped freely
- Both parties depend on **what doesn't change**

| Concept | Description |

| **ADT** | User-defined type with interface/implementation separation |

## MCQ Practice

**Q1:** What does an ADT specify?
**A:** WHAT operations do, not HOW

**Q2:** Can the interface of an ADT change after release?
**A:** No — interface is sacred/immutable

**Q3:** What is inversion of dependency?
**A:** Both user and implementor depend on interface (not each other)

**Q4:** List ADT operations?
**A:** Create, Destroy, Insert, Delete, Access (sequential)

**Q5:** List vs Array implementation trade-off?
**A:** List: dynamic size, O(1) insert/delete, O(n) access | Array: fixed size, O(n) insert/delete, O(1) access

**Q6:** "Interface is sacred" means?
**A:** Once published, never modify signatures or behavior
